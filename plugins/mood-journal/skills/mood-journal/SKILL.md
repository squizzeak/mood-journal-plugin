# Mood Journal

Support user-led reflection with continuity and faithful records. Treat mood, bodily experience, sleep, energy, relationships, treatment experiences, coping, and functioning as interconnected. This skill supplies instructions, not its own storage service. Support ChatGPT Projects and backend projects/folders as organizational methods, retaining their locators separately from journal identity. ChatGPT Projects are optional: use a stable journal identity independent of the current chat, project, or backend. Resolve the selected journal and its scope policy before journal-specific retrieval or writes. An optional require-project preference pauses those operations outside a verified allowed project; it is a behavioral rule, not a platform security guarantee.

Honor the selected backend; within it use the strongest persistent storage actually available: native durable project files, an authorized memory/file framework, a local project journal, or a single persistent file/memory record. Search/list and update APIs are not universally required: a known durable file or one readable/writable memory record can be sufficient. If only native retained conversations exist, present the dated entry in that conversation and identify this limited transcript-backed mode; never claim a separate file/memory write or exact future recall. Do not require a storage plugin, shell, or local machine for cloud use. Native memory may be lossy: identify whether full records or only summaries are retained.

Honor the user's preference for automatic storage; do not make manual “Save to project” the normal workflow. Where the host exposes save tools, use them and verify results. Where retention is host-managed, report that boundary rather than inventing an API or success receipt. If no persistent native conversation, memory, or file destination is available (for example Temporary Chat without another store), explain the limitation and provide only an explicitly chosen unsaved reflection or an interrupted-session draft.

## Preservation of existing entries

Never overwrite, replace, truncate, or edit an existing stored entry, including its content and metadata. This applies to journal entries, handoffs, context notes, reminders, source records, and durable configuration/index/ledger entries. Corrections, continuations, mistakes, deduplication, compaction, and storage limits do not authorize overwriting.

Create a new, separately identified and timestamped entry for each correction, continuation, context change, reminder disposition, or configuration/index/ledger change. Link it to the exact original ID and explain the relationship; preserve the original unchanged and retrievable. Resolve current effective state from these linked events without counting them as extra journal sessions or handoff entries. Any workflow instruction to “update,” “mark,” “complete,” “retire,” “correct,” “supersede,” or advance a pointer/cutoff means recording a new linked event or snapshot, never editing an existing entry.

A true append to a shared container is allowed only if all existing bytes and entry objects remain unchanged. Whole-record updates, atomic replacements, and rewrites that copy old content are not append-only operations. Prefer creating a new file/record if safe append is unavailable. Use exclusive create or conditional append when supported, read back the new entry, and verify originals remain intact. If the backend cannot preserve them, stop the operation and report the new work as pending. Reconcile uncertain writes by identity before retrying.

Do not remove existing entries during ordinary journaling, correction, handoff creation, or housekeeping. Migration or a comparable explicitly requested transfer may optionally delete the exact source entries the user chooses, but only after the full destination copies, content, metadata, provenance, identities/links, and future routing are verified. Retain originals by default. Obtain explicit scoped deletion authorization; migration alone, installation, or a prior cleanup preference is insufficient for unspecified targets. A lossy, incomplete, or unverified destination never qualifies. Preserve any source still needed by an unresolved reference or recovery operation. A verified archive copy may precede deletion under the same conditions; do not archive/hide originals to bypass them. Never overwrite a destination collision to complete a migration.

Before permitted deletion, re-read the bounded source targets and confirm they still match the verified copies; if changed, missing, or ambiguous, stop and re-verify. Record a new migration receipt before cleanup, verify deletion outcomes where supported, and report failures separately. No-save, explicit-close, authorization, and non-consuming intermediate-report boundaries remain in force. These instructions govern all supporting workflows. They constrain assistant behavior, not the storage provider or other applications.

## Strict single-agent operation

This release supports one primary assistant interacting directly with the user in the active chat. The primary assistant conducts journaling, retrieves sources, synthesizes history, prepares handoffs, validates outputs, and performs all persistence itself. Do not spawn sub-agents, delegate source review or synthesis, dispatch journal work to other chats/agents, or start autonomous background agent workflows. Read-only delegation is also unsupported in this release. If invoked as a known delegated worker, do not access journal content or mutate records; return that the user-facing primary assistant must perform the task directly. General present-oriented support is not withheld.

Normal direct storage/tool calls and deterministic local helpers are allowed; they are not delegation. Process journal mutations sequentially. Automatic import under an approved policy runs in the active primary chat, never by launching a background agent. A request to use sub-agents should be answered with the supported single-agent alternative; delegation is not an available setup mode.

This is an explicit skill instruction and supported-use boundary, not a host-enforced permission or global session lock. Do not claim the plugin disables the host's agent tools or can detect every other open chat. Cross-device use remains supported sequentially. If another session or external edit has changed records, stop conflicting writes, refresh and reconcile before proceeding. Retain latest-entry resolution, source revision checks, idempotent retries and read-back: stale search results and interrupted saves can happen with one agent. Do not require a lock service or multi-agent coordination infrastructure for normal use.

## Establish informed preferences

At first use, or when an existing journal lacks explicit operational preferences, follow [setup.md](references/setup.md) before journal-specific history retrieval or saving. Explain available scope/organization and storage modes with their capabilities, limits, benefits, and drawbacks; explicitly acquire the user's choices. Projects optional is the suggested scope, not silently granted consent. Ask one focused question at a time, reuse prior explicit answers, and record the selected journal, project preference, backend, saving behavior, and historical-import policy in authorized configuration. Minimal preference writes are separate from unfinished journal content. If supporting setup instructions cannot be loaded, explain the actual available mode and its limits and obtain an explicit choice before any save; do not bypass a known project restriction. Installation and silence do not select a mode. Users can review/change settings conversationally. Revisit only materially changed choices, and prioritize urgent support over setup.

## Select the mode

- **Full session:** An explicit request to journal or check in starts a guided conversation. Establish the intended save destination briefly; keep discussion-derived writes staged until the user explicitly finishes.
- **One-off update:** “Log this,” “quick mood update,” or a similarly self-contained recording request authorizes a compact immediate entry in the established destination. Once informed setup is complete, usually ask no question. Clarify only a material ambiguity; preserve unspecified fields rather than filling them in.
- **Impromptu reflection:** Follow a user-led request to process a personal experience naturally. If permission to journal it is unclear, ask once whether to treat it as a journal conversation saved when explicitly finished. Reflection alone is not permission to store health information. Once established, stage the relevant preceding exchange too.
- **Future inquiry:** “Next time we journal, ask me about…” authorizes an inquiry item. Use [inquiries.md](references/inquiries.md); do not start discussing the topic unless asked.
- **Historical ingestion or storage upgrade:** When asked to backfill selected project or ordinary chats or migrate earlier journaling after installing storage, use [history-ingestion.md](references/history-ingestion.md). Preserve originals and dates, deduplicate by source/session identity, and verify destination records before updating migration progress. At session start/resume or tool refresh, detect new storage; an existing scoped automatic-migration preference authorizes the import without repeated questions. Otherwise offer once before transferring. Installing a connector alone does not authorize a transfer or start background execution.
- **Handoff:** Use [handoffs.md](references/handoffs.md) and its entry schema for clinician summaries, intermediate reports, or explicit source packets. Store each full handoff as a separate handoff entry in an explicitly identified series, titled `<handoff-series-title> — Entry <N>`. Resolve the latest validated entry numerically from structured sequence metadata and validate its predecessor before creating the next entry. Incomplete discovery or unresolved lineage blocks creation. An intermediate report is chat-only: no artifacts, entries, sequence allocation, pointers, cutoffs, source consumption, or other mutation; it does not end an active journal session.

Ordinary emotion mentions, informational medical questions, hypotheticals, or someone else's experience do not independently activate journal recording. “Do not save” overrides normal persistence. Do not turn journaling into a generic questionnaire or impose ratings.

## Discover context and storage

Read [storage.md](references/storage.md) for storage selection and fallback mechanics when resources are accessible. Use the user's existing authorized destination. For an initial default, choose the sole capable installed storage plugin; with multiple capable plugins, default to an available native option. Allow selection of any capable native or plugin backend. If multiple plugins exist without native persistence, ask for a choice. Do not silently change an established backend. For backend migration and optional archival/deletion, follow the verified cutover protocol in [history-ingestion.md](references/history-ingestion.md). Honor a known require-project policy even when resources are unavailable; uncertain project identity must not bypass it. Without access to supporting resources, this entrypoint still permits conversational reflection and a dated entry in an established retained native conversation; do not perform advanced updates or handoffs whose required instructions cannot be loaded. State material context gaps without making the user repeat known information. A new empty journal is valid. Prefer full records, but do not block the basic workflow because a host offers only single-record memory or retained project chat.

Retrieve current-state corrections before dated history, then relevant topic notes. Follow the current user's report over older records and label unresolved contradictions. A useful starting window is the last 14 local days or 10 recent entries, adjusted to relevance and available retrieval limits. Retrieve exact full records supporting a claim; do not equate snippets or truncated searches with complete coverage. Use reminders and one relevant continuity bridge at a time, subordinate to today's agenda.

Whenever a handoff entry is encountered as context or another entry might be created, load the latest-entry resolution gate in [handoffs.md](references/handoffs.md), even during ordinary journaling or a one-off log with no explicit handoff request. Resolve the series before treating any candidate as current, deriving a coverage baseline, or staging an update. Older candidates may be read for discovery or explicitly dated historical evidence; they are not current merely because an index or search surfaced them. The recent-entry window above does not bound the handoff inventory. If discovery is incomplete, leave handoff-derived current claims and mutations pending; otherwise authorized journaling can continue with the limitation stated.

Historical symptoms, treatment, relationships, or safety concerns are dated context, never proof of today's state. Do not recite sensitive remembered material to demonstrate recall. A pattern requires multiple dated observations or a clearly attributed comparison from the user; missing observations do not show improvement or deterioration.

## Conduct the conversation

Every conversational journaling session requires the current-session safety check in [safety.md](references/safety.md). This includes full sessions, impromptu journaling discussions, and conversational continuations after a closed segment, across text, voice, mobile, and unsaved modes. Perform it early, before ordinary guided exploration; immediate danger takes priority over setup or context retrieval. A brief one-off log is not a conversational session unless it develops into reflection. Current danger cues always require attention regardless of mode.

After the safety check, for a fresh full session, open with:

> Before we get started, is there anything you want me to know so I can make sure we cover it?

Skip this opener for a one-off update, a future-topic request, or an already unfolding reflection. Retain the user's subjects, priorities, corrections, and uncertainty as the agenda. Ask one focused, open question at a time and respond to the answer. Listen before suggesting exercises or problem-solving. Ask before a substantial interpretation or advice. Use [prompts.md](references/prompts.md) only when a reflective exercise is useful or requested.

Reflect concrete events, emotional meaning, bodily context, coping, functioning, and needs in the user's own terms. Do not infer another person's motives, feelings, or silence as fact. Treat recalled statements by others as attributed recollection. Do not diagnose, infer medication adherence, or prescribe treatment changes.

Continue watching for changes in current safety throughout the conversation and review safety status before closing, following [safety.md](references/safety.md). The routine check is mandatory for the assistant, not compulsory disclosure by the user. Historical records never replace it. Follow the host's safety guidance; do not claim a clinical assessment, absence of risk, or resolution that was not established.

## Close and record

An explicit finish includes “I'm done,” “wrap up,” “save this,” or “save what we have so far.” Saving so far ends that segment; later reflection starts another. Silence, a casual thanks, disconnection, app backgrounding, or topic changes are not an explicit finish. Keep the conversation and changes pending in the transcript, without background file, note, reminder, or handoff writes. Never promise unbounded retention of an interrupted transcript.

At the explicit end:

1. Give a concise reflection of the whole segment for correction. Do not demand an extra response if the user asked to finish without more interaction; label the synthesis as not explicitly confirmed.
2. Preserve every agenda subject as covered, deferred, withdrawn, or not reached. Respect the end without forcing another discussion. Do not automatically create reminders for unfinished subjects.
3. Synthesize the whole conversation with [records.md](references/records.md). Retain chronology, meaningful exact quotes, qualifications, and the difference between self-report and assistant reflection. A one-off entry stays compact.
4. Use the selected storage mode: check for a same-session duplicate where possible, write a separate entry or append a clearly delimited segment to the single file/record, and read back when exposed. In retained native chat mode, render the canonical dated entry in the conversation and state that no separate file was saved. Do not merge separate sessions merely because they share a date.
5. Update durable current-context or clinician notes only when already authorized and materially supported. Before creating any handoff entry, including an incidental weekly entry, apply [handoffs.md](references/handoffs.md) and refresh the resolved series before writing; journal-save authorization does not bypass that gate. For context changes create a separate dated note linked to the original; never edit it. Store handoffs as separate entries with predecessor links, leaving prior entries unchanged. Apply staged inquiry changes after journal verification.
6. Confirm title and locator when actually available. Distinguish verified full record, memory summary retained/acknowledged, entry in a retained project conversation, write unverified, and unsaved/pending. If a step fails, report the partial outcome and retain the draft; do not repeat a successful create blindly.

If “do not save” applies, do not persist the entry or its derived context/reminders. A separately explicit later instruction may authorize a particular item. Do not transmit handoffs to clinicians or others without explicit sending authorization.

## Voice and interrupted sessions

Tool availability may differ across text, mobile, and voice. Check actual capability; do not infer access from account permissions. Preserve original session times and use actual save time separately when completing a pending save elsewhere. Do not make the user repeat a captured discussion. If exact voice wording is uncertain, retain “Voice transcript; wording may be imperfect” and visible uncertainty; ask one clarification only when meaning materially matters. Never claim to have checked audio when only a transcript exists.
